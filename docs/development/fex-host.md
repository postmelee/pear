# FEX and Wine CPU integration development

On October 8, 2026, Task #5 freshly rebuilt the selected Wine/FEX pair and passed
five original x64 Windows fixtures from empty synthetic prefixes on ARM64 macOS
26.5.2 (25F84). Every case returned 42 and passed current development authorization,
owned cleanup and native process/image observations without observed Rosetta use.
The [Stage 6 report](../../mydocs/working/task_m1_5_stage6.md) and
[sanitized observations](../../mydocs/working/task_m1_5_stage6_observations.json)
record the exact evidence. These results do not establish Steam or Megabonk support.

## Source and ownership

Retain Wine C and FEX C++/assembly at the [recorded source pins](../source-qualification.md#selected-input-set).
The original [Wine series](../../runtime/wine/patches/series.json),
[FEX service series](../../runtime/fex/patches/series.json),
[Wine memory supplements](../../runtime/fex/patches/memory-series.json),
[FEX memory source graph](../../runtime/fex/patches/memory/source-graph/derivatives.json),
and final [Wine](../../runtime/fex/patches/integration/series.json) and
[FEX](../../runtime/fex/patches/integration/fex-series.json) integration series
have separate identities. Preserve their order, attribution and upstream policies.
No commercial runtime or Rust rewrite is required by this path.

Wine supplies the actual PE/ARM64X role selection, native services and private
memory owner. FEX supplies x64 decoding, IR, ARM64 generation and guest-state
reconstruction. The selected translator owns its registration and execution
lifetimes. Generated bytes are staged as non-executable data, published through
the single-address owner, and changed only after managed executors drain.
Native API calls and callbacks retain explicit continuation ownership. The
[source design](../../mydocs/tech/task_m1_5_memory_design.md) explains the current
locks, cooperative suspend, invalidation and refusal boundaries.

The 1,588,985,856-byte JIT/PE reservation is virtual address space, not measured
resident memory. The finite bookkeeping estimate is 12.5 MiB within 16 MiB for
one Context and up to three participating translated threads. It excludes ordinary
engine allocations and does not set game capacity. The historical 256 KiB
prototype limit is not a Megabonk requirement.

## Reconstruct the recorded development candidate

This is a developer workflow using verified prepared inputs. It is not a download
or installation flow for players. Read the [Wine host guide](wine-host.md) for
pinned tools and actual macOS development authorization. Normal Hardened Runtime,
library validation and the role-specific provisioning grant remain required.
Do not pass credentials or private profiles through Git or public artifacts.

The current constructors accept the recorded source/tool preparation receipts:

| Input | Required material |
|---|---|
| `PEAR_WINE_OWNER` | Preserved source and manifest from the selected Stage 3 Wine owner construction |
| `PEAR_WINE_BASE` | #4's final ARM64EC companion receipt and pinned tool references |
| `PEAR_FEX_OWNER` | Source85 full FEX source, materialized manifest and source/tool bindings |
| `PEAR_CROSS_CLANG` | Verified native llvm-mingw clang from that tool preparation |
| `PEAR_OWNER_LAUNCH` | Recorded native owner launcher fixture |
| `PEAR_WINE_PROFILE` | Local, currently valid Wine Loader development profile |
| `PEAR_REUSE_SOURCE` | #7 source snapshot with the signing/supervisor functions pinned by `memory_wine_runtime.py` and `memory_wine_run.py` |

Set these shell variables to the corresponding local paths. Prepared source trees
are checked byte-for-byte and copied into new directories; old objects are not
copied. Source preparation and receipt admission are still staged developer work:
a clean checkout does not contain these private build records, and a different
preparation or host cannot inherit their hashes. Same-host reconstruction here
does not establish independent or clean-machine reproduction.

From the repository root, use fresh output names:

```sh
python3 tools/fex/reconstruct.py --component wine \
  --base "$PEAR_WINE_OWNER" --baseline "$PEAR_WINE_BASE" \
  --output .build/task5/final-wine
python3 tools/fex/reconstruct_fex.py \
  --base "$PEAR_FEX_OWNER" --wine .build/task5/final-wine \
  --output .build/task5/final-fex
python3 tools/fex/reconstruction_cases.py \
  --wine .build/task5/final-wine --fex .build/task5/final-fex \
  --compiler "$PEAR_CROSS_CLANG" --helper "$PEAR_OWNER_LAUNCH" \
  --profile "$PEAR_WINE_PROFILE" --reuse "$PEAR_REUSE_SOURCE" \
  --output .build/task5/final-cases
python3 tools/fex/reconstruction_services.py \
  --build .build/task5/final-fex --output .build/task5/final-services
```

The workflow preserves source manifests, command logs, actual module inspection,
signatures and observed results. Failed or incomplete records are not a passing
candidate. The constructors retain the existing bounded build monitor and serial
heavy-operation lock; do not delete inputs or change tools during a run. The
ordinary library/service fixture uses no restricted JIT operation.

## Interpret the checks

| Check | Observed behavior and limit |
|---|---|
| x64 API/callback | File, time, event and native-to-x64 callback roundtrip; exit42 |
| Worker/TLS | Isolated worker TLS, normal return and self-thread teardown; exit42 |
| Code invalidation | Both threads observe changed code; failed removal preserves live mappings; exit42 |
| Exceptions/guard | Handled UD2, guest context edits, nested native call and ordinary data guard; exit42 |
| Suspend/context | Running translated loop pauses, R12 is read/changed, then resumes; exit42 |
| Native caller refusal | An ordinary ARM64 caller without translator identity receives `PEAR_FEX_UNAVAILABLE`; its fixture exits68 as expected |
| Native services | Each UnixLib passes eight services, seven mapping controls, 26 policy controls and two-worker cleanup; no guest execution |

The x64 cases use the same reconstructed component bytes and independently
initialized synthetic prefixes. Each observed 41 native process-translation
results and more than 16,000 ARM64 image events. These are instrumented correctness
observations, not a full module timeline or performance/power measurement.

The native caller refusal is a negative control: it does not grant ordinary
callers access to the translator's memory interface. The old native fixture's
20-control expectation was updated for the current 12-setting policy (26 checks);
its original failure remains recorded. No runtime permission was relaxed.

Wider CPU/ordering conformance belongs to #6; complete process/module observation
to #10; required i386 Steam helpers to the inspected Steam path; translated
